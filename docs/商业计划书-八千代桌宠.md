# Kagami桌宠 商业计划书

**项目名称：** Kagami桌宠（Yachiyo Desktop）
**一句话定位：** 一只住在 Windows 桌面上的 Live2D 伙伴——用番茄钟陪你专注，用养成让你愿意回来，用本地 AI Agent 帮你干活。
**项目阶段：** 核心技术底座（v1）已完成并通过 Release 实测；商业化功能（v2）已完成架构设计与分阶段实施计划，待开发。
**文档日期：** 2026-09
**版本：** 1.0

---

## 摘要

### 我们在做什么

Kagami桌宠是一款 **Windows 桌面常驻 AI 伙伴软件**。它不是一个玩具式桌宠，也不是一个纯聊天机器人，而是把三件原本分离的事放进同一个常驻进程：

| 能力 | 解决的问题 | 用户获得的价值 |
|---|---|---|
| **番茄钟 / 专注计时** | 拖延、注意力碎片化 | 有人陪着，专注这件事变得可感知 |
| **养成系统** | 单机工具缺乏回访理由 | 专注本身产生成长反馈，形成正向循环 |
| **本地工作区 AI Agent** | 通用 AI 助手与"我的电脑"隔着一层 | Agent 在你授权的目录内读写文件、操作桌宠自身 |

三者咬合在同一只角色身上：**专注产生经验 → 经验改变角色状态 → 角色状态影响提示与语气 → 提示把你拉回专注**。

### 凭什么能做

项目的技术底座已被真实验证，不是文档里的设想：

- **架构选择：** Rust（Tauri 2）+ Vue 3 + PixiJS 8 + Live2D。相比主流 Electron 方案，常驻桌面软件的内存量级差异是数量级的。
- **常驻开销已实测：** Release 构建、真实模型探针计数，30 FPS 可见状态平均 **CPU 4.64%**（整机 12 逻辑处理器口径）、15 FPS **3.17%**，**隐藏与最小化状态下模型更新/绘制增量为 0**。这不是估算，是带 SHA-256 的可复现实测数据。
- **工程严谨性可验证：** 12 项 JavaScript 测试 + 5 项 Rust 业务测试 + 2 项验收状态测试、`cargo clippy -D warnings` 全绿、性能测量流程可复现（记录可执行文件 SHA-256 与提交号）、验收工具在检测到中断时会主动失败退出而不是给出好看的平均值。
- **安全设计前置：** 本地优先、密钥不落前端、文件访问走 Rust 侧 `canonicalize` + 路径前缀校验。

### 商业设计

面向 **知识工作者 / 开发者 / 学生** 的桌面常驻工具市场，采用"免费底座 + 订阅增值 + 企业定制"三层模式。AI Agent 的推理成本由用户自备 API Key 承担（BYOK），因此**毛利结构不依赖规模摊薄，第一笔订阅即为正毛利**。

### 需要什么

比赛阶段申请：技术评审与资源对接，用于完成 v2 六个阶段（Phase 7–12）的工程实现、真实用户内测与首版商业化打包。

## 第一章 市场与机会

### 1.1 三个正在交汇的趋势

**趋势一：虚拟陪伴从"玩具"变成"软件品类"。**
全球虚拟宠物模拟器 App 市场 2025 年规模约 **30.4 亿美元**，预计 2035 年达 **72 亿美元**，年复合增长率 **9.1%**（2026–2035）。驱动因素中，AI 与 AR 对交互体验的提升被明确列为核心趋势（[WiseGuyReports：Virtual PET Simulator App Market](https://www.wiseguyreports.com/reports/virtual-pet-simulator-app-market)）。

**趋势二：桌面级 AI 伴侣硬件与软件同步起量。**
桌面 AI 伴侣机器人（Desktop AI Robot Companion）赛道被多家机构列为独立细分，有报告预测其规模在 2032 年将达到约 **8.79 亿美元**；国内媒体援引启信宝数据，"陪伴机器人"整体市场规模剑指千亿人民币量级（[格隆汇：桌面AI伴侣机器人市场趋势](https://dxpress.gelonghui.com/p/4607946)、[证券之星：启信宝数据洞察](http://finance.stockstar.com/IG2026072100021882.shtml)）。

这里存在一个被忽视的结构性机会：**硬件陪伴产品需要用户额外花钱买设备，而桌面软件的边际成本接近零，且用户一天 8 小时都在电脑前**——需要陪伴的场景早已存在，只是缺少形态合适的产品。

**趋势三：专注力工具是被验证的付费市场。**
以 Forest 为代表的专注类 App 已证明"用角色/树木的成长反馈来激励专注"是可规模化的商业模式（[Forest 官方](https://www.forestapp.cc/)、[Google Play](https://play.google.com/store/apps/details?id=cc.forestapp)）。但这一品类几乎全部在**手机**上，而知识工作者的深度工作发生在**电脑**上——在电脑前工作时，手机上的专注 App 恰恰是最先被扔到一边的东西。

### 1.2 机会窗口：三个圈的交集几乎无人占据

```
        Live2D / 二次元角色表现
                 ▲
                ╱ ╲
               ╱   ╲
              ╱  ★  ╲
             ╱       ╲
   长期常驻 ◀─────────▶ 真正有产出的 AI Agent
   （低开销）              （能读写你的文件）
```

- **圈一：Live2D 桌宠。** 存在多年，但绝大多数是"看得见的装饰"，不产生任何实际产出。
- **圈二：AI Agent / 编程助手。** 能力强大，但形态是"窗口"——你要主动打开它、切换过去；它不会主动出现在你视野里。
- **圈三：专注力工具。** 有方法论、有付费意愿，但形态是手机 App 或网页，与真实工作场景错位。

**交集（★）的现状是空的。** 现有玩家要么做"好看的装饰"，要么做"强大的工具"，没人认真做"**有存在感、有产出、开销低到可以永远开着**"的第三类东西。

### 1.3 目标用户与痛点

| 用户群 | 规模特征 | 核心痛点 | 我们的答案 |
|---|---|---|---|
| **独立开发者 / 程序员** | 付费意愿最高，是 AI Agent 的重度使用者 | 长时间编码易疲劳；AI 助手需要切窗口；想要"陪伴感"但不想被打扰 | 常驻桌面的 Agent + 角色情绪反馈，提问不用切窗口 |
| **考研 / 考证备考人群** | 规模大，专注时长是刚需 | 番茄钟 App 在手机上，学习在电脑上；一个人学很难坚持 | 桌面上不会消失的倒计时徽标 + 连续天数 |
| **二次元 / Live2D 爱好者** | 传播力最强 | 喜欢 Live2D，但官方模型多为展示用途，缺"每天都会打开"的理由 | 模型 + 实用功能，给爱好一个日常使用场景 |
| **创意工作者（设计 / 写作）** | 中等规模 | 工作流碎片化，缺乏节奏感 | 专注-休息节律由角色主动提示 |

**共同痛点的一句话总结：** 电脑前的八九个小时里，用户既缺一个"陪伴者"，也缺一个"工具"，而现在市场上的产品**只能二选一**。

## 第二章 产品

### 2.1 产品形态

一个**透明、无边框、可拖动的常驻小窗口**（340×440），Kagami站在桌面任意位置；右键弹出气泡菜单，托盘提供完整控制，设置与对话在独立窗口中打开。

设计原则：**不打断用户已有的工作流**。桌宠不做全屏遮挡、不弹模态框、不需要用户切换应用。

### 2.2 功能规划与实现状态

> **诚实标注**是这个项目的一贯做法，也是为了评审可核对：下表逐项区分"已实现（v1）"与"已设计待开发（v2）"。

#### v1：已实现并通过验证的能力

| 功能 | 状态 | 说明 |
|---|---|---|
| 透明无边框常驻窗口 | ✅ 已实现 | 340×440 逻辑像素，可拖动，任务栏隐藏 |
| Live2D 模型渲染 | ✅ 已实现 | PixiJS 8 + easy-live2d 0.4.4，2 张 4K RGBA 贴图 |
| 待机表现 | ✅ 已实现 | 眨眼、呼吸、物理摆动 |
| 四个表情切换 | ✅ 已实现 | smile / squint / tears / teardrop |
| 鼠标跟随 | ✅ 已实现 | 头部、眼睛、身体平滑朝向鼠标，**鼠标移出窗口仍有效**（使用桌面全局坐标） |

#### v2：已完成设计、待开发（Phase 7–12）

| 功能 | 设计要点 | 商业价值 |
|---|---|---|
| **番茄钟** | Rust 侧独立后台任务 + 绝对时间戳（存 `deadline` 不存 `remaining`）；隐藏、最小化、系统睡眠均不停表；崩溃后可恢复上次会话 | 建立每日使用习惯的核心抓手 |
| **养成系统** | 专注分钟 → 经验；等级曲线、心情值（下限 20，**不做惩罚性表现**）、连续天数、解锁项；衰减惰性结算，不跑常驻循环 | 长期留存与订阅转化 |
| **本地工作区 Agent** | 用户显式授权目录 → Rust 侧 `canonicalize` + 路径前缀校验；8 个工具（读写文件、grep、切表情、控制番茄钟）；写操作默认关闭且需逐次确认 | 付费核心；形成"离不开"的工作价值 |
| **对话窗口** | 独立 720×560 窗口，**不加载第二份 Live2D Core**；SQLite 持久化会话与消息；流式输出按 ~50ms 节流刷新 | 承载 Agent 交互 |
| **持久化底座** | 原子写 + `schemaVersion` + 损坏回退默认值，绝不 panic | 商业软件的可靠性基线 |
| **凭据安全** | API Key 存 Windows 凭据管理器（keyring），**只在 Rust 侧读取，不回传前端**，日志脱敏 | 企业采购的合规前提 |

### 2.3 关键产品决策（体现产品判断力）

1. **不做惩罚性养成。** 心情值下限锁死 20，不做"生病/离家出走/死亡"。理由写在设计文档里：**桌宠不应该因为用户忙而惩罚用户**。这是与大量养成游戏相反的取向，也是"陪伴"与"成瘾机制"的分界。
2. **AI 推理成本由用户自备 Key 承担（BYOK）。** 既避免成为"烧钱换用户"的推理补贴生意，也让高级用户和企业用户对成本有掌控权。项目本身不需要为每次对话垫付成本。
3. **文件访问权限不交给前端。** 即使前端被注入，也无法越界读取工作区外的文件——所有访问经 Rust 命令，每次校验真实路径前缀。
4. **不引入 RAG / 向量库。** 先用 `grep` + 用户显式指定文件。理由是避免过度设计，等真的遇到"找不到"的问题再评估。

## 第三章 竞争分析

### 3.1 竞争格局

| 维度 | 传统桌宠<br>（Shimeji / 各类 Live2D 桌宠） | AI 桌面助手<br>（通用聊天客户端） | 手机专注 App<br>（Forest 等） | **Kagami桌宠** |
|---|---|---|---|---|
| 角色表现力 | 强 | 无 / 弱 | 弱（图形化） | **强（Live2D + 物理 + 跟随）** |
| 常驻开销 | 中～高 | 高（Electron 常见） | —（不在 PC） | **低（实测隐藏态 0 更新）** |
| 实际产出 | 无 | 强 | 无 | **强（读写工作区文件）** |
| 主动存在感 | 有 | 无（需主动打开） | 无（在手机上） | **有（角色反馈 + 专注徽标）** |
| 本地数据 / 隐私 | 本地 | 云端为主 | 云端账号 | **本地优先，密钥不出 Rust** |
| 从零开始学习用户 | 无记忆 | 有记忆但不了解你 | 有统计 | **养成 + 会话 + 工作区上下文** |

### 3.2 我们的三个真实优势

**优势一：常驻开销的工程事实，而不是营销话术。**
桌面常驻软件最大的死因是"用户觉得它占资源"。我们是在 Release 构建下、用探针统计真实模型 `update`/`draw` 调用次数得出的数据，并记录了硬件型号、系统版本、缩放比例、贴图哈希与可执行文件 SHA-256。**结论可复现、可被第三方推翻** —— 这类数据在同类竞品中几乎没有公开。

**优势二：Architecture 决定了成本结构。**
Rust + 系统 WebView2（Tauri 2）不打包 Chromium；对话窗口明确不加载第二份 Live2D Core；养成衰减惰性结算不跑常驻循环。这些是**写在代码约束里**的决定，而不是事后优化。

**优势三：AI Agent 与角色是同一个进程的两面。**
Agent 能调用 `set_expression`、`start_pomodoro`、`get_growth_summary` —— 也就是说，**Agent 可以操作角色本身**，角色也能反映 Agent 的状态。这是"聊天机器人 + 桌宠"简单拼接做不到的，因为它们的架构里角色和 Agent 是两套东西。

### 3.3 我们承认的劣势

| 劣势 | 现状 | 应对 |
|---|---|---|
| 付费能力验证尚未开始 | v2 未开发，无真实付费数据 | 比赛阶段以技术验证 + 内测意向收集替代；不虚构收入 |
| 单一角色（Kagami） | v1 固定模型 | v2 非目标；先验证"功能价值"，再评估角色商店（角色为最强潜在增值点） |
| 无动作文件 | 模型缺 `.motion3.json` | 表现限于表情与参数，**不承诺"角色做专注动画"**；真实动作需补美术资源 |
| Windows 单平台 | 第一版仅 Windows | Tauri 天然跨平台，macOS 为 v3 候选 |
| 团队规模小 | 个人/小团队 | 靠架构清晰与阶段交付保证质量，不追求功能数量 |

## 第四章 技术与壁垒

### 4.1 技术架构

```
┌─ Vue 窗口层 ───────────────────────────────────────────────┐
│ main 桌宠 340×440      settings 360×360+     chat 720×560  │
│ 表情·气泡菜单·倒计时   设置/成长/专注配置      工作区·对话·工具卡片 │
└──────────────────┬─────────────────────────────────────────┘
                   │ invoke / listen（薄封装，命令名集中在 src/api/）
┌──────────────────┴─ Rust 服务层 ────────────────────────────┐
│ store.rs     原子持久化 + schemaVersion + 损坏回退            │
│ clock.rs     可注入时钟（测试用）                             │
│ pomodoro.rs  纯状态机 + 独立后台任务                          │
│ growth.rs    经验/等级/心情结算（纯函数 + 惰性衰减）            │
│ workspace.rs 工作区注册 + 路径边界校验                        │
│ fs_tools.rs  受限文件工具（给 Agent 用，不暴露给前端）          │
│ provider/    OpenAI 兼容 · Anthropic · Fake（测试）           │
│ agent.rs     Agent 循环 + 工具注册表 + 流式转发                │
│ secret.rs    keyring 封装（密钥不出 Rust）                    │
│ db.rs        rusqlite：会话与消息                             │
│ broadcast.rs 统一事件广播                                     │
└─────────────────────────────────────────────────────────────┘
```

**五条贯穿全局的架构原则：**
1. **Rust 是唯一事实源** —— 状态变更先在 Rust 完成并落盘，再广播事件；前端只做视图。
2. **定时用绝对时间戳** —— 存 `deadline` 不存 `remaining`，避免漂移与睡眠后错乱。
3. **网络与文件 IO 只在 Rust 侧** —— 前端拿不到 API Key，也不开放 fs scope。
4. **纯逻辑写成纯函数** —— 状态迁移与数值结算不依赖 Tauri、不依赖系统时间，直接可单测。
5. **不引入新框架** —— 继续用 composables，不引入 Pinia / Vue Router / UI 组件库。

### 4.2 已验证的性能数据（Release 实测）

**测试环境：** Intel Core i5-13420H（8 核 / 12 逻辑处理器）、约 16 GiB 内存、Intel UHD Graphics、Windows 11 家庭中文版 10.0.26200、1920×1200 @60Hz、系统缩放 125%、平衡电源方案。无 DevTools，无 Vite，使用 `--no-bundle --features perf-audit` 优化构建。

| 状态 | 阶段时长 | 模型 update / draw（次/秒） | 平均 CPU（整机口径） | Private Bytes 中位数 | GPU 共享内存 |
|---|---:|---:|---:|---:|---:|
| 可见，30 FPS | 120 秒 | **29.49 / 29.49** | **4.64%** | 497.3 MiB | 229.8 MiB |
| 可见，15 FPS | 120 秒 | **14.90 / 14.90** | **3.17%** | 500.1 MiB | 229.3 MiB |
| 隐藏 | 120 秒 | **0 / 0** | 采样精度下约 0% | 430.9 MiB | 230.8 MiB |
| 最小化 | 120 秒 | **0 / 0** | 采样精度下约 0% | 501.7 MiB | 231.3 MiB |

- **30 → 15 FPS，平均 CPU 下降约 32%**（按精确值复算 31.8%），证明帧率控制有真实收益。
- **暂停 / 恢复：** 计划 22 次暂停后检查，**暂停期间最大更新增量、绘制增量均为 0，恢复首帧最大模型步长为 0 秒**；原始记录最终计数为 `pauses 24 / resumes 23`，全程模型实例 ID 唯一、前端 error 与 unhandledrejection 计数为 0。
- **GPU：** 本机为集成显卡，GPU 专用内存计数全程为 0，GPU 共享内存约 230 MiB；隐藏时纹理保留、显存不随绘制停止释放，符合设计意图。
- **可复现指纹：** 测量 exe SHA-256 `E39541AF…B89CC93`、源代码基准提交 `56f8fc6`、两张贴图各自的 SHA-256 均已归档，第三方可复算。
- **进程构成：** 主程序 1 个 + WebView2 子进程 7 个（Rust host / browser / renderer / gpu-process / crashpad / 3×utility），已逐一标注角色 —— 这也说明"只看主进程内存"会大幅低估真实开销，我们主动把这一点写进测量口径。
- **口径透明：** 三种内存指标口径不同、不可相加；4K 贴图 128 MiB 与 8K 贴图 512 MiB 是按 RGBA8 计算的**理论纹理数据量，不等同于实测内存**；本次未测整机功耗，因此**不把 CPU 降幅换算成续航提升**。

**未被美化的部分（同样重要）：** 30 分钟连续可见待机**未通过验收** —— 进行到约 390 秒时被额外的隐藏操作打断，记录被标记为 `continuousVisibleIdlePassed: false`，汇总脚本**拒绝输出容易误导的混合状态平均值**，归档中也没有 `complete.json`。项目选择暂缓该验收并如实归档，而不是宣布"长期稳定"。这说明团队对数据的态度：**宁可留一个未完成项，也不给一个好看的假结论。**

**同样如实标注的还有：** 原生托盘菜单点击、手动拖动、系统关闭按钮转隐藏、跨不同缩放显示器的拖动仍属**人工验收项**（本机只有一台显示器）；安装包体积与启动耗时**尚未测量**（本次没有制作安装包）。这些数据在本文档中一律不作为卖点引用。

### 4.3 测试与质量

| 层面 | 现状 |
|---|---|
| 前端单元测试 | 12 项通过（`node --test`，无额外测试框架依赖），覆盖渲染策略、模型时钟、模型布局、加载失败恢复、鼠标跟随边界、手势判定、菜单状态机、设置快照版本比较 |
| Rust 测试 | 5 项业务测试 + 启用 `perf-audit` 时的 2 项验收状态测试，覆盖表情白名单、设置版本号、窗口布局几何（含多屏与缩放）、验收工具错误状态 |
| 测试设计特点 | 时钟测试**直接提取已安装依赖中的真实 `TimeManager` 执行**，而非 mock —— 覆盖首次启动、暂停五分钟后恢复、长帧与负时间差 |

### 4.4 壁垒与可复制性

坦率地说，**功能本身是可被复制的**（一个周末就能做出会动的桌宠）。真正难以复制的有四层：

1. **性能工程细节的积累** —— 上游库补丁、ticker 生命周期、暂停恢复时间基准、4K/8K 贴图取舍。这些是踩坑换来的，且是常驻软件的核心体验。
2. **安全模型的正确性** —— 路径边界校验、密钥不出 Rust、最小权限 capabilities。做错一次就是安全事故。
3. **架构克制** —— 明确写下"不做什么"（不做 RAG、不做命令执行、不做云同步、不做多角色）。范围控制能力决定了产品能否交付。
4. **角色的排他性** —— 内容侧壁垒。角色 IP 一旦与产品体验绑定，后来者复制功能也复制不了"感觉"。

### 5.2 单位经济模型（自下而上估算，非实际数据）

| 项目 | 金额（元/年） | 说明 |
|---|---:|---|

### 5.3 为什么不选其他模式

| 备选模式 | 为什么不选 |
|---|---|
| 广告 / 弹窗 | 破坏"陪伴"的产品内核，且与常驻桌面的低干扰设计直接冲突 |

| 云端账号绑定数据 | 与"本地优先、数据只在本机"的隐私主张冲突；作为**可选**的云备份保留 |

## 第六章 市场进入策略

### 6.1 三阶段增长路径

**第一阶段：内容冷启动（0 → 1,000 用户）**
- 主阵地：B 站、小红书、知乎、V2EX、少数派。桌宠是天然的**录屏传播素材**——"它跟着我的鼠标转头"只需要 5 秒就能被理解。
- 打法：发布制作过程（如何用 Rust + Live2D 做一个低开销桌宠），用真实性能数据（CPU 4.64%、隐藏 0 更新）建立技术可信度，吸引开发者群体。
- 成本：接近零，全部为自制内容。

**第二阶段：功能驱动增长（1,000 → 10,000 用户）**
- 核心动作：发布番茄钟 + 养成版本，切入"备考/自习"内容生态。这时候的传播语言从"好看的桌宠"变成"陪我一起学习的小家伙"。
- 建立内测群，用真实反馈驱动迭代（设计文档里已经预留了 6 个需要用户确认的决策点，说明这个流程已经在运转）。
- 引进第一个付费点：角色皮肤包（低决策成本，验证付费意愿）。

**第三阶段：价值驱动与 B 端（10,000+ 用户）**
- 发布本地工作区 Agent，向开发者群体扩展；这是从"陪伴工具"升级为"生产工具"的一步，直接对应更高的付费意愿。
- 探索企业版：中小研发团队的统一配置分发与团队专注看板。
- 引入真实动作资源与新角色，做内容电商。

### 6.2 渠道与获客

| 渠道 | 适配用户 | 内容形态 |
|---|---|---|
| B 站 / 小红书 | 二次元爱好者、学生 | 桌宠实机演示、制作过程、模型效果对比 |
| 知乎 / 少数派 / V2EX | 开发者、知识工作者 | 技术长文：为什么选 Tauri 而非 Electron；如何把常驻开销做到 4.64% |
| GitHub（开源核心） | 开发者 | 开源客户端底座，建立技术信任与贡献渠道；增值内容与 Agent 高级功能保持闭源 |
| 高校社群 / 自习室社群 | 备考人群 | 番茄钟使用场景内容、连续天数挑战 |

**开源策略说明：** 开源底座是**获客手段而非商业模式**。它把"性能与隐私"的主张变成可验证的事实，同时让开发者成为第一批传播者。商业化功能（养成内容、Agent 增强、角色包）保持闭源。

### 6.3 合规与伦理

- **数据本地化：** 数据只在本机（`app_data_dir`），不设云端同步为默认。
- **密钥安全：** API Key 存 Windows 凭据管理器，不回传前端，日志脱敏。
- **文件访问边界：** 用户显式授权目录，Rust 侧逐次校验真实路径前缀；写权限默认关闭、逐次确认。
- **AI 内容合规：** 通过 BYOK 使用第三方模型，需要在用户协议中明确模型服务由第三方提供；不上传用户文件到我们自己的服务器。
- **伦理取向：** 明确拒绝成瘾机制 —— 心情值下限 20、不做惩罚性表现、不做"不打开就失去什么"的设计。这是产品价值观，也是与监管趋势一致的方向。

## 第九章 风险与对策

| 风险类别 | 具体风险 | 影响 | 对策 |
|---|---|---|---|
| **技术** | 番茄钟挂到渲染 ticker 或依赖窗口可见性 | 隐藏窗口就停表，功能性地错误 | 独立后台任务 + 绝对时间戳；验收明确覆盖隐藏与睡眠场景 |
| **技术** | 系统睡眠后时间错乱、重复结算 | 剩余时间错误 | 只用 `deadline` 判定，唤醒后一次性补齐；不累加计数 |
| **技术** | 流式 token 洪泛拖累渲染 | 页面卡顿、30 FPS 预算被侵占 | 事件按 `messageId` 聚合，前端约 50ms 节流刷新；Phase 12 强制性能回归 |
| **安全** | API Key 泄露 | 严重后果 | 只存 keyring，不回传前端；日志脱敏；`set_api_key` 无回显 |
| **安全** | 前端被注入后越界读文件 | 读取工作区外的敏感文件 | 不放宽前端 fs scope；Rust 侧 `canonicalize` + 前缀校验；专项测试 |
| **成本** | 上下文爆炸 / 费用失控 | 用户请求失败或成本超预期 | 预算裁剪 + 最大轮数上限 + 工具输出截断；BYOK 下成本由用户掌控 |
| **产品** | 范围蔓延（语音、RAG、命令执行） | 交付周期失控 | 设计文档明确列出"非目标"，需求变更先改文档再动代码 |
| **商业** | 付费能力未被验证 | 商业模式破产 | 比赛阶段不虚构收入；先做内容冷启动与内测意向收集，用真实数据决定投入 |
| **商业** | 大厂跟进（如系统级 AI 助手内置角色） | 被降维打击 | 壁垒放在角色内容与垂直工作流整合上，而非通用能力 |
| **合规** | Live2D 商用授权 | 无法商业化 | 商业化前完成授权确认，或评估替代方案 |
| **合规** | AI 生成内容监管 | 上架受阻 | 第三人模型服务、本地数据不上传、明确用户协议与内容边界 |
| **运营** | 单人团队的健康与持续性 | 项目中断 | 文档先行、阶段化交付、纯函数与测试降低维护成本 |

### 10.2 需要验证的关键假设

| 假设 | 验证方式 | 失败意味着什么 |
|---|---|---|
| 用户会让桌宠长期常驻（而非新鲜几天就关掉） | 内测 30 日留存、常驻时长埋点（本地统计，不上传） | 形态不成立，需要重新设计交互 |

### D. 引用这些数据时的三条纪律

1. **区分测量状态：** "隐藏/最小化 CPU 约 0%"的准确表述是**采样精度下约 0%**；原始样本中各有 1 个切换边界样本非零（3.09% / 1.54%），已按方法学排除在有效窗口外。
2. **区分理论值与实测值：** 128 MiB / 512 MiB 是纹理数据量计算，不是应用实测内存；实测内存以 summary.json 的 Private Bytes 与 Working Set 为准，且两者不可相加。
3. **区分计划值与实测值：** "暂停/恢复 22 次"是计划口径，原始记录最终为 `pauses 24 / resumes 23`；两者都写出来，避免被质疑口径不一致。

### E. 立项以来的关键工程判断

1. 为什么用 Tauri 而不是 Electron？—— 常驻软件的内存与启动开销是体验的一部分；系统 WebView2 不重复打包浏览器内核。
2. 为什么模型要单独做 4K 贴图？—— 原始 8K 贴图按 RGBA8 计算基础纹理数据合计 512 MiB；4K 后为 128 MiB 量级，且在 340×440 的显示尺寸下 4K/8K 未见明显脸部差异。
3. 为什么隐藏时要真的停 ticker，而不是只隐藏 DOM？—— 实测证明增量确实归零；"看不见就不渲染"是常驻软件的基本礼貌。
4. 为什么番茄钟不能用 `setInterval`？—— 窗口隐藏时计时器不可靠，且睡眠唤醒后会错乱。改用 Rust 后台任务 + 绝对时间戳。
5. 为什么不让前端直接读文件？—— 前端是攻击面；权限放在 Rust 侧逐次校验，前端被注入也越不了界。
6. 为什么不做 RAG？—— 先用 `grep` 验证真实需求，避免为想象中的问题付出复杂度。
7. 为什么心情值有下限 20？—— 陪伴产品不应该惩罚用户的忙碌。
