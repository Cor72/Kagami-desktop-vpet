# 八千代桌宠：Agent 模式与情境感知（设计提案）

日期：2026-09-14。状态：**外部提案，待作者确认**。
前置：[v2 设计方案](2026-09-12-yachiyo-companion-v2-design.md)、[商业计划书](../../商业计划书-八千代桌宠.md)、[最小实现设计](2026-09-10-yachiyo-mvp-design.md)。

> 本文**不推翻** v2 方案。Phase 7–12 的架构、阶段划分、验收标准全部保持原样。
> 它只补两处 v2 尚未定义的内容，并给出与现有阶段对接的方式：
>
> 1. **Agent 的准入模型**：聊天模式 / Agent 模式、工作区条目分类型、工具集如何随之收放。
> 2. **主动行为策略**：角色在用户没提问时该不该开口、说什么、多久一次、什么时候必须闭嘴。

## 一、动机

### 缺口 A：Agent 与聊天没有区分

v2 的 Phase 11 与 Phase 12 里，`agent.js` 与对话窗口是同一套东西，工具集固定。用户无法表达「我现在只是想闲聊」和「我现在要你动我的文件」这两种完全不同的意图，权限也无法随意图收放。

现有设计的 `write_file` 只写了「需确认」。但**没有定义怎么确认**——在一个没有 diff 视图的弹窗上点「是」，用户并不知道会改掉哪几行。这不是权限不够，是权限无法被理解。

### 缺口 B：没有「主动」这一层

Phase 7–12 全部是「用户发起 → 系统响应」：点番茄钟、问 Agent、选工作区。

但商业计划书 1.2 给这个产品下的定义是：

> **有存在感、有产出、开销低到可以永远开着**

「存在感」只能来自主动。而设计文档里没有任何一个阶段在实现它——最接近的是 Phase 8 的「进行中每 5 分钟一次轻微提示（可关闭）」，而且限定在番茄钟进行中这一个场景。

### 本文提出的两个方案

| 缺口 | 方案 | 落点 |
|---|---|---|
| A | 双模式 + 工作区条目分类型 | 与 Phase 10、11 对接 |
| B | 情境感知 + 频率预算 + 静默规则 | 新增，可与 Phase 8 并行 |

**两点都不引入新框架、不新增窗口、不占用气泡菜单球位。**

## 二、与 v2 的关系

**不改动任何既有阶段的目标、验收标准与顺序**，只做三件事：

1. **给 Phase 10 的工作区条目加一个类型字段**（目录 / 文件），使权限的「给谁、给多少、能不能写」可以被用户理解。Phase 10 已有的 `canonicalize` + 白名单校验 + 逃逸测试全部沿用。
2. **给 Phase 11 的工具集加一个准入开关**（模式），让工具集的收放成为用户可见的动作，而不是一个内部常量。
3. **新增一块 v2 未覆盖的能力**（主动行为），建议作为与 Phase 8 并行的独立阶段，不阻塞任何既有阶段。

> 有一处例外需要写明：若「工作区条目分类型」被采纳（见决策点 2），Phase 10 的**实现方式**要从「单一工作区目录 + 前缀校验」调整为「条目白名单 + 分类校验」。
> Phase 10 的**原有验收项全部保留**——`../` 逃逸被拒、指向工作区外的符号链接被拒、大小写与分隔符变体正确规范化、合法子路径通过；在此之上**新增**一组针对「外部只读条目」的用例（见第九节）。变的是校验实现与测试覆盖，不变的是这些边界都必须被守住。

## 三、核心概念：两种模式

对话窗口内提供一个模式切换（放在窗口内部，**不占气泡菜单球位**，因此与 v2 §4.8 的菜单方案 A/B/C 之争无关）。

| | 聊天模式（默认） | Agent 模式 |
|---|---|---|
| 给模型的工具 | **空集** | 工作区只读工具 + 桌宠控制工具 |
| 能接触文件吗 | 不能 | 只能接触已授权的工作区条目；**文件条目永远只读** |
| 上下文里有什么 | 角色设定 + 对话历史 | 角色设定 + 对话历史 + 工作区清单 + 情境摘要 |
| 适用场景 | 闲聊、问问题、陪聊 | 看代码、查资料、整理笔记 |

**关键约束：模式只决定「给模型哪些工具」。能碰哪些文件是独立的一层，由工作区授权决定，开关无权放开。**

这一点必须有，否则会退化成「前端一个开关就等于拿到文件访问权」。能力边界必须在 Rust 侧：

```
前端模式开关  →  只是选择要注册哪些工具
Rust 工具实现 →  每次都重新校验路径是否落在已授权白名单内
```

用户就算手动改了前端状态，工具层依然会拒绝越界路径。

## 四、工作区：条目分两种类型

### 4.1 一个工作区，两种条目

**不新增第二个权限模型，只给工作区的条目加一个类型字段。**

工作区仍然是 v2 §4.5 定义的那个东西——用户显式授权、Rust 侧逐次校验、写入默认关闭。变化只有一处：**授权条目分两种类型**。

| | 目录条目 | 文件条目 |
|---|---|---|
| 怎么加进来 | 系统目录选择器（v2 原有方式） | 拖拽投放，或文件选择器 |
| 权限 | 读写，**写默认关闭** | **只读，物理上没有写入通道** |
| 用户的心智模型 | 「这是我的项目」 | 「这是我给你的资料」 |
| 校验 | 同一套 `canonicalize` + 白名单校验 | 同一个函数 |
| 第一版是否可用 | 读可用，写未开放 | 完全可用 |

选择合并而不是并行做两套的理由：

1. **保住 v2 的安全叙事。** 写权限**只属于目录条目**，而且默认关闭——「AI 物理上无法修改你的文件」这个承诺完整保留。文件条目是只读的，多开一条只读通道不会削弱写入侧的边界。
2. **保住拖拽体验。** 不懂路径概念的用户只需把文件拖进来，不必理解「选择文件夹」对话框。
3. **实现只有一套。** `workspace.rs` 的条目结构加一个 `type` 字段，校验函数按类型决定是否允许写。这不是两套并行的权限系统。
4. **对 v2 的改动小。** `add_workspace` 本来就要处理「重复添加同一目录时复用记录」，加类型是扩展而非重写。
5. **用户看得懂。** 界面上就是一个列表，两种条目各带一个图标，只读的那个画一把锁。

> **与阶段的关系**：`write_file` 在第一版不实现（见 5.1），所以**第一版里没有任何条目是可写的**——目录条目在第一版同样是只读。写入能力开放后，只有目录条目会被写入；**文件条目永远只读**。

### 4.2 拖拽投放文件条目

把文件拖进工作区，落地为**文件条目**。

**支持这个做法**，因为：

- Tauri 2 原生支持文件拖放（`onDragDropEvent`），前端能直接拿到绝对路径，改造成本低。
- 对不懂路径概念的用户，拖拽是唯一自然的方式。

**但有一条必须写死：拖进来的是引用，不是复制。**

| | 复制文件 | 记录路径（推荐） |
|---|---|---|
| 大文件 | 慢、占空间（一个 500 MB 的视频要复制一份） | 瞬间完成 |
| 原文件更新后 | 工作区里的是旧副本 | 永远读到最新 |
| 用户删除原文件 | 工作区里还有一份 | 路径失效，需要优雅报错 |
| 存储占用 | 翻倍 | 零 |

所以「拖进来」的实际动作是：**记录绝对路径 → `canonicalize` → 加入只读白名单**。界面上可以做成「文件卡片」，让用户感觉东西被放进来了，但底层是引用。

拖入整个目录也支持，但**必须弹一次确认**（见 4.4）。

### 4.3 路径安全

Phase 10 已有的校验全部保留，另外必须覆盖这几个新增的边界：

1. **符号链接与快捷方式。** 用户拖进来一个指向 `C:\Windows` 的软链接，`canonicalize` 之后会解析到真实路径。**解析后的路径要重新过一遍校验**，不能只校验用户拖进来的那个字面路径。
2. **拖入目录后的递归。** 允许，但深度与条数都要有上限（见 4.4）；`node_modules`、`.git` 之类的目录要有默认忽略规则。
3. **路径失效。** 原文件被移动或删除后，工具要返回明确的「路径已失效」错误，并在界面上把那张卡片标灰，而不是抛异常或静默返回空。
4. **大小写与分隔符。** Windows 路径大小写不敏感，白名单比较必须规范化后再比，避免 `C:\Foo` 与 `c:\foo` 被当成两个路径。
5. **引用内容会变。** 文件条目是引用而非副本，好处是永远读到最新，代价是**对话历史里已引用的旧内容会过期**——模型可能以为自己看的还是最新的。第一版采用简化处理：`read_file` 的返回值里带上**文件的最后修改时间**，让模型至少能看到时间戳。不做更复杂的失效检测。

### 4.4 边界与限制

| 项 | 建议值 | 理由 |
|---|---|---|
| 工作区条目上限 | 32 条 | 超过这个数，用户自己也管不过来 |
| **拖入目录时的确认** | 显示「这将授权 AI 读取 N 个文件」并要求确认 | 手滑拖进 `C:\Users\xxx` 就等于授权了全部个人文件；把文件数量摆出来本身就是最有效的劝阻 |
| 拖入目录的递归深度 | 3 层 | 再深基本是依赖目录，没有阅读价值 |
| 单次 `list_files` 返回 | ≤ 200 条 | 保护上下文 |
| 单文件读取 | ≤ 64 KB | 超出时要求模型先用 `grep` 定位再读区间 |

## 五、工具设计：轻量化的三层含义

「轻量化」这个方向同意，但要拆成三件不同的事，否则容易只做了第一件。

### 5.1 第一层：工具数量

聊天模式 **0 个工具**。

Agent 模式第一版只给 **5 个**，比 v2 的 8 个少，分三类：

| 工具 | 归类 | 权限 | 说明 |
|---|---|---|---|
| `list_files` | 工作区 | 只读 | 看工作区结构，限深度与条数 |
| `grep` | 工作区 | 只读 | 搜索优先，替代整目录读取 |
| `read_file` | 工作区 | 只读 | 单文件，有大小上限 |
| `set_expression` | 桌宠 | 写（表情） | 复用现有表情白名单校验 |
| `get_context` | 情境 | 只读 | 取情境摘要（见第六节） |

**第一版不做 `write_file`。** 理由：写入需要 diff 视图、逐块采纳、撤销、并发冲突处理，工作量远大于其余四个工具之和；而没有 diff 的写入确认等于盲签。先把「能看、能反应」做扎实，写入单独作为第二个阶段。

番茄钟与养成相关的三个工具（`get_pomodoro_status` / `start_pomodoro` / `get_growth_summary`）保留在 v2 计划里，但**等 Phase 8 / 9 落地后再注册**，不阻塞本提案。

### 5.2 第二层：工具输出的硬上限

这一层比第一层重要。工具返回值会**全部进入上下文**，一个 5000 行的文件读进来，上下文直接爆掉。

| 工具 | 硬上限 |
|---|---|
| `list_files` | 深度 ≤ 3，条数 ≤ 200，超出时返回「已截断，共 N 条」 |
| `grep` | 命中 ≤ 50 条，单条 ≤ 200 字符 |
| `read_file` | 单文件 ≤ 64 KB；超出时提示改用 `grep` 定位 |
| 单轮工具返回值合计 | ≤ 上下文预算的 25% |

最后一行是关键：**不管是哪个工具，加起来不能吃掉超过四分之一的预算。** 否则一次搜索就能把历史记录挤出去。

### 5.3 第三层：渐进式访问顺序

在系统提示词里写死工具的使用顺序偏好：

```
先 list_files 看结构 → 再 grep 定位 → 最后才 read_file 读具体片段
```

这和 v2 §4.6 已经写的「优先用搜索代替整目录读取」是同一件事，值得在提示词里再强化一次——**模型默认行为是急着读整份文件**。

### 5.4 工具的作用范围：不加参数

工作区里同时可能有目录条目和文件条目，于是有个问题：`grep` 该搜哪里？`list_files` 该列哪里？

**答案是不新增 `scope` 参数——路径本身就是范围。**

| 工具 | 参数 | 路径为空时的含义 |
|---|---|---|
| `list_files` | `{ path? }` | 列出所有已授权条目的根 |
| `grep` | `{ pattern, path? }` | 搜索全部已授权条目 |
| `read_file` | `{ path }` | 路径本身就是范围 |

唯一新增的规则是「**路径为空 = 全部条目**」，而这条规则复用同一套白名单校验，不引入任何冗余逻辑，也不增加工具 schema 的体积。

另外，**工作区条目清单直接写进系统提示词**（最多 32 条，每条一行「类型 + 路径」），而不是为它增加一个查询工具。这样模型不必先花一轮工具调用去问「我有什么可用」。

## 六、情境感知：用轻量信号替代「看屏幕」

> **先明确动机，因为这一节最容易被读成留存手段。**
>
> 主动行为的目标是**生动性**，不是留存。它只做一件事：让角色对「你此刻在做什么」有反应。搭话说完就说完了——**不需要用户回应，不理它没有任何损失，更不存在「不打开就失去什么」。**
>
> 商业计划书 §6.3 列出的三条反成瘾标准，本节逐条对照如下：
>
> | §6.3 的标准 | 主动行为的做法 |
> |---|---|
> | 不做惩罚性表现 | 忽略它没有任何后果 |
> | 不做「不打开就失去什么」 | 没有连续签到、没有断签、没有亲密度掉级 |
> | 明确拒绝成瘾机制 | 说完即止，不要求用户回应；连续被忽略会**自动降频**（§6.5） |
>
> 判断标准是「这句话此刻是否有趣」，而不是「这句话能否让用户多待一会儿」。两者冲突时，选择不说话。

### 6.1 为什么不做定时截图

「让 AI 一分钟看一次屏幕」这个思路，问题不在隐私，在三件事同时不成立：

**一、和这个项目最自豪的工程成果冲突。** README 的标题级结论是「隐藏时更新/绘制为 0 次/秒，30 FPS 占 4.64% CPU」。一分钟截一次全屏、编码、上传 1–2 MB，与「开销低到可以永远开着」是正面冲突的。

**二、成本发生在用户没提问的时候。** 一张 1080p 截图约 1100 个图片 token。一分钟一张 = **一小时六七万 token**，而这是在用户没有向它要任何东西的情况下烧的。

**三、违背本项目自己写的设计原则。** 商业计划书 2.1：

> 设计原则：**不打断用户已有的工作流**

作为对比，v2 里作者自己定的最高主动频率是「番茄钟进行中每 5 分钟一次轻微提示」。一分钟一次、全时段，差了一个量级。

### 6.2 更好的信号源：拿得到，而且更准

「用户屏幕上有什么」这个信息，**大部分不需要截图**。Windows 提供一组轻量 API 就够：

| 信号 | 取法 | 能得到什么 |
|---|---|---|
| 前台窗口 | `GetForegroundWindow` + `GetWindowText` | 窗口标题，例如 `pomodoro.rs — yachiyo-desktop — Visual Studio Code` |
| 前台进程 | `GetWindowThreadProcessId` + 进程名 | `Code.exe` / `chrome.exe` / `WINWORD.EXE` |
| 空闲时长 | `GetLastInputInfo` | 距离上次键鼠输入过了多久 |

Rust 侧用官方 `windows` crate 就能调，量级是几十行。

把三者结构化成给模型看的一小段文本：

```text
应用：代码编辑器
文件：pomodoro.rs
空闲：2 分 30 秒
```

**约 30 个 token。对比一张截图的 1100 token，便宜三十多倍，而且信息更准**——截图还要 OCR 才知道你在改哪个文件，前台窗口标题直接写着文件名。

> token 数是按常见视觉模型分块计价方式的**估算值**，只用于比较量级，不作为精确预算；实际值应在 Phase 11 联调时用真实供应商核对。

### 6.3 两段式：本地判断，才调模型

这是整个方案里最重要的一条结构决策。**必须区分「采集」与「调用模型」——昂贵的只有后者。**

```text
低频采样信号（本地，读几个廉价 API，成本可忽略）
        │
        ├─ Rust 侧规则引擎判断「该不该开口」
        │      （只在信号发生变化时才执行判断）
        │
        ├─ 不该 → 丢弃。不调模型，不花钱
        │
        └─ 该 → 才把情境摘要发给模型，生成那句话
```

采集方式取**低频采样**（默认 5 秒一次），一次只读三个廉价 API，成本可以忽略。真正必须禁止的是**定时调用模型**——那是这段流程里唯一花钱的动作。

规则引擎是一个纯函数（`should_speak(signal, state, now) -> Option<Intent>`），可以用 `node --test` 或 `cargo test` 覆盖，不需要真实时间、不需要网络。

这样绝大多数采样都不会走到模型那一步，行为可预测、可测试。**是否开口由本地规则决定，不由模型决定**——模型只负责把已经决定要说的话说好。

### 6.4 触发规则

规则判断是事件驱动的（信号发生变化才判断），触发条件如下：

| 信号变化 | 触发 | 需要模型吗 | 状态 |
|---|---|---|---|
| 空闲 ≥ 5 分钟（可配 3–10） | 闲置问候（固定文案） | 否 | 本提案 |
| 从空闲回到活跃 | 打招呼 | 否 | 本提案 |
| **检测到某个应用启动** | 角色反应，例如打开编辑器 / 游戏时各一句 | 否 | 本提案 |
| 同一文件停留 ≥ 25 分钟 | 「卡住了吗」 | 是 | 本提案 |
| 番茄钟完成 | 汇报 + `smile` | 否 | **等 Phase 8 落地后由作者决定** |
| 非工作类应用连续 ≥ 20 分钟 | 温和提醒（可关） | 是 | **待定——最容易变成说教，建议最后做** |

**「应用启动」这一条值得单独说。** 它是一个**事件**——不需要判断时长、不需要轮询、也不需要调模型，一张「进程名 → 文案」的映射表就够了。v1 可以内置一张表（编辑器 / 浏览器 / 音乐 / 游戏各几句），用户自定义映射留到后续。这是成本最低、见效最快的一条，**建议第一个做**。

### 6.5 频率预算

**先纠正一个容易犯的错：防骚扰靠的是「什么时候绝对不说」（§6.6 静默规则），不是靠把频率调低。**

一个上限为「每 20 分钟 1 次」的功能，用户一整天可能一次都碰不到——**看不到的功能等于不存在**。正确做法是按触发类型分别给额度，而不是设一个全局低频闸门：

| 触发类型 | 额度 | 为什么 |
|---|---|---|
| **事件型**（应用启动、番茄钟完成） | 同类事件每次至多 1 句；同类之间冷却 ≥ 5 分钟 | 天然低频——用户不会每分钟开一次编辑器，不需要再压 |
| **状态型**（闲置问候、回到活跃） | 每次离开只触发 1 次；**同类之间冷却 ≥ 20 分钟** | 关键不是全局上限，而是「一次离开只说一次」 |
| **提醒型**（停留太久、长时间刷非工作应用） | 每天 ≤ 3 条 | 这类最容易变成说教，收紧 |
| 每日总量 | ≤ 30 条（可配） | 兜底，不是主力约束 |
| **连续被忽略 3 次** | 自动降频，同类冷却翻倍 | **这一条才是核心** |
| 用户随时可关 | 「今天别烦我」按钮，当天不再主动 | |

**「连续被忽略自动降频」是本节最重要的机制。** 额度决定最坏情况，降频决定这个功能会不会自己收敛到安静。一个不需要用户主动关闭、会自己学会闭嘴的功能，才有可能被长期开着。建议把它做成**不可关闭**的机制。

### 6.6 静默规则

| 条件 | 行为 |
|---|---|
| 前台是全屏应用（游戏、演示） | 静默 |
| 当天被手动静音（托盘「今天别烦我」） | 静默，跨天自动失效 |
| 最近 30 秒内有键盘输入 | 延后，等停下来再说 |
| 番茄钟 focus 中 | 静默 |

### 6.7 隐私边界

用户的顾虑是对的，但**「可关闭」这个答案不够**。建议按下面的方式做：

**先把两样东西分开，它们的敏感程度完全不同：**

| 信息 | 例子 | 敏感吗 | 怎么处理 |
|---|---|---|---|
| **应用名**（进程名） | `GenshinImpact.exe`、`Code.exe`、`WeChat.exe` | 基本不敏感 | **直接给**，并映射成中文名 → 打开游戏时角色知道「你在玩原神」 |
| **窗口标题** | `招商银行 - Chrome`、`张三 - 微信`、`pomodoro.rs - VS Code` | **可能很敏感** | 只对**已知编辑器**提取文件名，其余**整条丢弃** |

于是「打开某个游戏会不会被知道」的答案是：**会，但只知道你在玩那个游戏**——因为那是应用名。而你在微信里跟谁聊天，AI 只会知道「你在用微信」。

| 原则 | 做法 |
|---|---|
| 采集全在本地 | 信号采集、规则判断全在 Rust 侧，默认**不发送**任何数据 |
| 只在开口时才外发 | 只有决定说话那一刻，才把**归类后的情境摘要**发给模型 |
| 原始窗口标题不外传 | 标题只在本地用于分类与编辑器判定；**非白名单应用的标题一律不进模型**。浏览器标签页标题可以暴露你在看哪个网页，这类内容没有一条链路流出去 |
| 不采集输入内容 | 键盘只用来判断「有没有在输入」这个布尔量，不记录按键 |
| 用户可以看见它看见了什么 | 设置页提供实时预览：「角色现在能看到：代码编辑器 / pomodoro.rs」 |
| **首次主动说明** | 启用时由角色自己说清三件事：采集什么、用来做什么、怎么关 |
| 一键总开关 | 关闭后不采集、不外发、不主动说话 |

最后三条建议认真做。**用角色自己的话把「我能看到什么、怎么关掉」说清楚，比在隐私条款里写一百字管用。**

### 6.8 明确不做

- 不做定时截图 / 录屏
- 不记录键盘输入内容
- 不上传原始窗口标题
- 不做云同步
- 不做后台常驻的**模型调用**（低频采样随主动策略的开关启停；关闭后不采集、不外发、不发言）

## 七、主动说话的内容：模板兜底

主动说话的内容分两级：

| 级别 | 来源 | 成本 | 何时用 |
|---|---|---|---|
| 兜底 | 本地模板（每类 3–5 条） | 零 | 未配置 API Key，或调用失败 |
| 增强 | 模型按角色语气生成 | 一次调用 | 已配置 API Key 且可用 |

**兜底这一级的价值容易被低估：它让「主动行为」完全不依赖 Phase 11。** 没配 API Key 的用户也能被角色搭话，功能不是残缺状态。这也让主动行为可以与 Phase 8 并行推进，不必等 AI 接通。

本文不定义角色语气与人格。**「说什么」属于角色设定，应当单独成文**，并且是 Phase 11 组装系统提示词的前置输入。

## 九、实施阶段建议

不改变 v2 的 Phase 编号，只在既有阶段上挂接，并新增一个独立阶段。

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 与 Phase 8 并行 | 情境采集 + 规则引擎 + 模板兜底发言（**不需要 AI**） | 无 |
| 与 Phase 10 对接 | 工作区条目类型、拖拽投放、路径校验 | Phase 10 |
| 与 Phase 11 对接 | 模式开关、只读工具集（**暂不含 `write_file`**） | Phase 11 |
| 新增 Phase 13 | `write_file` + diff 视图 + 逐块采纳 + 撤销 | Phase 12 |

**`write_file` 单独成一个阶段**是本提案最主要的节奏建议。「AI 帮你改文件」听起来是一件事，实现上是三件事：写入、可审查、可撤销。缺了后两个，前一个没人敢用。

### 验收标准

沿用 v2「每个阶段必须可运行、有测试、有验收」的要求：

**情境感知部分**

- [ ] 规则引擎为纯函数；`should_speak()` 的边界用例（刚好到阈值、连续触发被预算拦下、当天被静音）全部有测试，且测试不依赖真实时间与网络。
- [ ] 不配置 API Key 且断开网络时，主动发言仍正常工作（走模板兜底）。
- [ ] 把系统时间调到 23:30，确认进入静默，不再主动发言。
- [ ] 连续忽略 3 次后，确认同类触发的冷却时间自动翻倍。
- [ ] 反复空闲 / 返回切换，确认「一次离开只说一次」生效，而不是每次回来都开口。
- [ ] 隐藏窗口时主动策略仍在运行，且**没有**产生任何模型调用。
- [ ] 设置页的「角色现在能看到什么」预览与采集到的实际内容一致。

**工作区部分**

- [ ] 拖入文件后确认**原文件未被复制**（对比磁盘占用与文件修改时间）。
- [ ] 拖入一个指向工作区外的软链接，确认解析后的真实路径被拒绝。
- [ ] 删除已授权的原文件后，工具返回明确的失效错误、界面卡片标灰、程序不崩。
- [ ] 在能力白名单层面核对**文件条目**没有任何写入通道，而不只是界面上没有按钮。
- [ ] 拖入一个包含大量文件的目录，确认弹出「这将授权 AI 读取 N 个文件」并要求确认。

**性能回归**

- [ ] 用 `app/scripts/measure-performance.ps1` 对比引入前后：30 / 15 FPS 的 CPU 占用，以及隐藏时是否仍为 0 次更新与绘制。

## 十、决策点

### 10.1 本提案已定，供作者复核

| # | 决定 | 理由 |
|---|---|---|
| 1 | **双模式**：聊天模式 0 个工具，Agent 模式按需收放工具集 | 用户需要能表达「我现在只想闲聊」 |
| 2 | **不新增第二个权限模型**，只给工作区条目加 `type`（目录 / 文件）；文件条目永远只读，目录条目写默认关 | 保住 v2 的安全叙事，同时拿到拖拽体验；实现只有一套 |
| 3 | 拖拽投放采用**引用路径**而非复制文件 | 大文件不占空间；原文件更新后永远读到最新 |
| 4 | **第一版不做 `write_file`** | 写入是「写入 + 可审查 + 可撤销」三件事；只读版即便有 bug 也不会破坏任何东西 |
| 5 | 工具**不新增 `scope` 参数**，路径即范围；条目清单写进系统提示词 | 零新增参数、零新增查询工具 |
| 6 | 主动行为**默认开启 + 显式关闭按钮 + 首次主动说明** | 默认关闭等于没有存在感；但没有透明度的默认开启不可接受 |
| 7 | 情境信号**分两级处理**：应用名直接给（映射中文名），窗口标题只对已知编辑器提取文件名、其余整条丢弃 | 知道你在玩哪个游戏，但不知道你在跟谁聊天 |

### 10.2 仍需作者确认

1. **Phase 10 的实现方式是否允许调整。** `type` 字段是对 v2 §4.5 的扩展：原有验收项全部保留，另需新增面向「外部只读条目」的用例。这个改动范围是否可以接受？
2. **主动行为部分是否纳入本期。** 若不纳入，删掉第六、七节与相关验收项即可，本提案其余部分不受影响（见 §12.1）。

## 十二、交付方式与待补充

### 12.1 关于交付方式

本提案以**一份文档、一个 PR** 提交。理由是两部分共用同一套背景——工作区里的条目既是 Agent 的输入，也是主动行为的信号来源，拆开后各自都要重复一遍动机与架构。

**但请在阅读时把它们当作可以分开取舍的两块：**

| 块 | 章节 | 分歧性质 |
|---|---|---|
| **A：Agent 模式与工作区条目** | 一、二、三、四、五、八、九、十节 | 技术分歧，适合在 PR 内直接讨论 |
| **B：主动行为策略** | 六、七节 | 涉及产品价值观（§6 开头已逐条对照商业计划书 §6.3），宜单独讨论 |

若只接受 A，删掉 B 的两节与对应验收项、**在同一个 PR 里追加一次提交**即可，不需要关闭重开。

### 12.2 待补充

以下三项都建议**单独成文**，不与本提案混在同一个 PR 里：

- **八千代的角色设定与系统提示词**。它是 Phase 11 组装消息的第一步，也是「对话像不像八千代」的唯一决定因素。
- **主动说话的具体文案与语气规则**（依赖上一条）。其中「应用启动」的进程映射表可以先于角色设定落地。
- **本地记忆**。让角色记住用户这件事，v1 建议做成**结构化条目 + 全量注入**：最多 N 条（如 50 条）带时间戳与主题标记的记忆，全部塞进系统提示词，不做检索。
  理由：角色感的来源是「她记得你上周说在准备面试」，而不是「她能检索到五万字的设定集」。**在条目规模到数千之前不需要向量检索**，这与 v2 §4.5「避免过度设计」的判断一致。
